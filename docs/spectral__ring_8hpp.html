Detailed Description

SPSC-Ringpuffer im Shared Memory für den hochratigen Spektral-/ FFT-Strom (#1 der Korrelationsanalyse).

Zweiter, vom TelemetryRing getrennter Ring. Grund für die Trennung: Der Massenstrom (#1) darf den Event-Strom (#2-#8) nicht verdrängen. Ein 1024-Punkt-Spektrum sind 4 KB pro Record, der feste 64-Byte-Payload des TelemetryRecord reicht dafür um Größenordnungen nicht.

UNTERSCHIEDE ZUM TelemetryRing

  1. VARIABLE SLOT-GRÖSSE. Die Slot-Größe hängt von fft_size ab, die erst zur Laufzeit feststeht. Deshalb kein typisiertes Array, sondern Byte-Offset-Arithmetik: slot_i = base + sizeof(Header) + i*record_stride. fft_size und record_stride stehen im Header, Python baut sein numpy-dtype daraus zur Laufzeit (siehe python/spectral_layout.py).
  2. MONOTONE INDIZES statt Modulo-Indizes. write_index/read_index zählen endlos hoch und werden NIE zurückgesetzt; der Slot ergibt sich per index % capacity. Der TelemetryRing nutzt dagegen Modulo-Indizes und opfert einen Slot, um "voll" von "leer" zu unterscheiden.
  3. SEQLOCK PRO SLOT. Zwingend, sobald drop-oldest aktiv ist, siehe unten.
  4. ZWEI GETRENNTE DROP-ZÄHLER, einer je Policy. Ein Drop bedeutet je nach Policy etwas völlig anderes:
    • drop-newest: der AKTUELLSTE Frame ist verloren, die Historie ist heil.
    • drop-oldest: ein ALTER Frame ist verloren, der Consumer sieht aber weiterhin die aktuellsten Daten. Für die Korrelation "Latenzausreißer vs. Buffer-Health" (Korrelation e) müsst ihr die beiden unterscheiden können, sonst ist die Aussage "Drops korrelieren mit Latenzspitzen" nicht interpretierbar.

Ownership-Regel wie beim TelemetryRing: Der C++-Core erzeugt und besitzt das Segment; Python öffnet nur (create=False) und unlinkt NIE.
