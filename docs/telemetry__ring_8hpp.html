Detailed Description

SPSC-Ringpuffer (Single-Producer/Single-Consumer) im POSIX Shared Memory, für den Telemetrie-/Event-Datenstrom C++ -> Python.

Entspricht dem "data" / "raw bytes"-Pfad im Architekturdiagramm (Core (C++) -> shared memory -> Rod (Python)). Dieser Ring ist für die niedrigratigen Telemetrie-Records (#2-#8 der Korrelationsanalyse: Kanal-Belegung, Detektions-Events, Latenz-Zeitstempel, Regler-Zustand, Aktor-Zustand, Erfolgs-Metrik, Buffer-Health) gedacht.

WICHTIG: Der hochratige FFT-/Spektral-Strom (#1) gehört NICHT in diesen Ring, sondern in einen zweiten, separaten Ringpuffer mit eigenem Layout (größere Slots, ggf. andere Overflow-Policy). Sonst verdrängt der Massenstrom die Events. Siehe Notiz "Zwei Ringpuffer" aus der Korrelationsanalyse.

Ownership-Regel (wichtig wegen Python resource_tracker):

  • Nur der Producer (C++, dieser Header) ruft create() auf und ist Eigentümer des Segments -> nur er darf destroy()/unlink() aufrufen.
  • Python öffnet das Segment ausschließlich mit multiprocessing.shared_memory.SharedMemory(name=..., create=False) und ruft NIEMALS unlink() auf. Siehe python/telemetry_layout.py.

Speicher-Ordering:

  • Producer: Slot vollständig schreiben, DANACH write_index mit memory_order_release vorrücken.
  • Consumer: write_index mit memory_order_acquire lesen, DANACH Slot lesen. read_index wird mit memory_order_release vorgerückt. Damit ist garantiert, dass der Consumer nie einen halb geschriebenen Slot sieht (kein "torn read").
