Detailed Description

Zero-Copy-Consumer für den von C++ geschriebenen TelemetryRing.

Öffnet ein bestehendes Shared-Memory-Segment (erstellt vom C++-Core)
und legt numpy-Views für Header und Slots darüber. Schreibt selbst
nichts außer dem read_index.

◆ check_stale()

None python.telemetry_layout.TelemetryRingReader.check_stale (   self) 
Prüft, ob unser Mapping noch das aktuelle Segment ist.

Hintergrund: Startet der Core neu, unlinkt er den Namen und legt ein
FRISCHES Segment an. Unser Mapping bleibt gültig, zeigt aber auf die
alten Pages -- die sich nie wieder ändern. Ein poll() darauf liefert
stillschweigend für immer nichts. Weil die alten Pages auch die alte
`generation` behalten, nützt ein Vergleich der Generation im eigenen
Mapping hier NICHTS -- geprüft werden muss gegen den NAMEN im tmpfs.
Deshalb der Inode-Vergleich.

Dies ist die Notlösung, solange es keinen CommandChannel gibt. Sobald
der Socket steht (Phase 2), erkennt Python den Core-Tod direkt am
EOF der Verbindung; dieser Check bleibt dann als billiger Zusatz.

Raises:
    StaleSegmentError: Segment wurde ersetzt oder entfernt -> der
        Aufrufer muss close() und neu open() machen.

Öffnet ein bestehendes Segment.

Args:
    shm_name: Name des Segments. Führende Slashes werden entfernt;
        "vusion_telemetry" und "/vusion_telemetry" sind äquivalent
        und treffen beide das C++-seitige shm_open("/vusion_telemetry").
    expected_capacity: Optional. Wenn gesetzt, wird gegen die im
        Header hinterlegte capacity_slots geprüft. Die tatsächliche
        Slot-Zahl kommt IMMER aus dem Header -- sie wird nicht mehr
        vom Aufrufer vorgegeben, damit C++- und Python-Seite nicht
        über einen von Hand gepflegten Wert auseinanderlaufen können.

Raises:
    RingNotReadyError: Segment fehlt/ist noch nicht initialisiert -> retry.
    RingSchemaError: inkompatibles Schema -> Neubau nötig.

◆ poll()

list[np.void] python.telemetry_layout.TelemetryRingReader.poll (   self,
bool   check_liveness = False 
) 
Liest alle seit dem letzten poll() neu geschriebenen Records.

Entspricht dem Consumer-Ablauf aus der Architekturbesprechung:
write_index (acquire-artig) lesen, neue Slots kopieren, read_index
vorrücken. numpy/Python garantiert keine echte acquire/release-
Semantik -- für den nicht-zeitkritischen Analyse-Pfad mit
Poll-Intervall (z.B. alle 10 ms) ist das akzeptiert und
dokumentiert, siehe Diskussion zu Cross-Language-Atomics.

Args:
    check_liveness: Wenn True, wird vorab check_stale() ausgeführt.
        Das kostet einen stat()-Syscall -- daher nicht bei jedem
        poll() sinnvoll, sondern z.B. jeden n-ten, oder immer dann,
        wenn längere Zeit keine Daten kamen.

Returns:
    Liste neuer Records (numpy structured scalars), älteste zuerst.

Raises:
    StaleSegmentError: nur wenn check_liveness=True.
