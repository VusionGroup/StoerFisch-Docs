StoerFisch

BLE-Spektrumanalyse und Störsender auf Basis eines HackRF One, aufgeteilt in zwei Prozesse:

Teil Sprache Aufgabe
Core (SDR, StoerFisch-Core) C++ HackRF ansteuern, FFT/Detektion/Regelkreis, Senden (Jamming/Replay), Sweep
Rod (rod, dieses Repo) Python + React Webserver + Web-UI: liest die Core-Daten, setzt Steuerkommandos ab

Beide laufen als eigenständige Prozesse auf demselben Host und reden über drei Kanäle: einen Unix-Socket (Kommandos) und zwei Shared-Memory-Ringe (Spektrum, Telemetrie).

Rod (Python + Web-UI) Core (C++, vusion_core_hackrf)
┌─────────────────────┐ ┌───────────────────────────────┐
│ Kommando-Client ────┼── Unix-Socket ─▶ /tmp/vusion_cmd.sock │
│ ◀──┼── Antwort ─────┤ │
│ Spektral-Reader ◀──┼── SharedMem ───┤ /vusion_spectral (FFT) │
│ Telemetrie-Reader◀──┼── SharedMem ───┤ /vusion_telemetry (Events) │
└─────────────────────┘ └───────────────────────────────┘

Der Core ist Owner der drei Ressourcen (legt sie an, räumt sie weg); Rod öffnet sie nur.

Voraussetzungen

Entwickelt/getestet unter Linux.

Gemeinsam

  • Linux

Rod

  • uv (Paket-/Env-Manager) — installiert nach ~/.local/bin/uv:
    curl -LsSf https://astral.sh/uv/install.sh | sh
  • Node.js 22 + npm

Core (nur für den Echtbetrieb)

  • HackRF One + libhackrf inkl. Tools:
    sudo apt install hackrf libhackrf-dev cmake pkg-config build-essential
  • C++26-fähiger Compiler (GCC 14+ / aktueller Clang) — der Core nutzt CMAKE_CXX_STANDARD 26.

Bauen

Core

cd StoerFisch-Core
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
# -> Binary: build/SDR

Rod

Wheel (self-contained: Python + gebautes Frontend + Core-Python-Bindings):

uv build
# -> dist/rod-<version>-py3-none-any.whl

Der Build-Hook (hatch_build.py) baut das Frontend beim Wheel-Build automatisch mit — für ein Release genügt also uv build --wheel.

Starten

Core + HackRF

# 0. SDR File ausführbar machen
chmod 774 SDR
# 1. Core starten (legt Socket + Shared-Memory an)
.SDR --freq 2440000000 --sample-rate 20000000
# 2. Rod starten
uv run rod

Aus dem Wheel (frischer Rechner)

uv pip install rod-<version>-py3-none-any.whl
uv build
uv run rod

Das Wheel enthält Python-App und gebautes Frontend — es braucht kein Node/npm mehr, nur Python ≥ 3.12. Nicht enthalten: die Core-Binary SDR und der HackRF-Treiber.

Socket- und Shared-Memory-Namen müssen zwischen Core (--socket, --*-shm) und Rod (ROD_CMD_SOCKET, ROD_SHM_*) übereinstimmen.

Die Python-Bindings des Cores (command.py, spectral_layout.py, telemetry_layout.py) spiegeln byte-exakt die C++-Header. Bei jeder Schema-Änderung im Core mitziehen - sonst lehnt der Core Kommandos mit SchemaMismatch ab bzw. die Ring-Reader lesen Unsinn.

Fehlersuche

Symptom Ursache / Abhilfe
Core nicht erreichbar beim Start Core läuft nicht, oder falscher Socket-/Shm-Name (Core-Flags ↔ ROD_*)
Jedes Kommando SchemaMismatch core/python/command.py älter als der Core — aktualisieren
Spektrum/Telemetrie steht während Sweep Der Core baut RX pro Schritt neu auf — Verweildauer groß genug wählen (≥ ~30 ms bei 20 MS/s)
